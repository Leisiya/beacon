# 上游成本、调价规则与毛利设计

更新日：2026-11-19（第二期同日完成）。业务时区 Asia/Shanghai，看板以人民币汇总。

## 用户已确认的口径

- Beacon 是转售：向中转站上游批量买额度，加价卖给客户，差价是毛利。
- 同一模型无论走哪家供应商，客户价格统一；每次调用的成本随实际渠道不同。
- 上游涨价时对所有客户立即生效，包括已充值余额（即改模型售价，而不是只改新收款给多少额度）。
- 上游涨价后跟不跟、涨多少，必须在后台可配置，不写死。
- 不知道上游如何报价：按调研，中转站多为 New API / One API，成本 = 官方美元价 × 上游分组倍率 × 充值比例（¥/上游 $1）。

## 实测依据（novaris）

- novaris 基于 New API，`/api/status` 显示 `price=1`（¥1 充 $1 额度）、`quota_per_unit=500000`。
- 用渠道密钥请求 `GET /api/log/token` 可取该密钥最近 1000 条调用；每条带对方扣除的额度、`other.group_ratio`（CCMax蒸馏专用分组 = 1.8）和 `request_id`。
- 对方 `request_id` 与本站日志 `upstream_request_id` 完全一致；7 次调用 token 数一致，合计扣 11968 额度，等于对方账户实际减少量。

## 第一期：上游真实成本（已实现）

- `beacon_upstream_rates`：按渠道追加的进价，含生效时间、每单位上游额度的人民币成本、操作人与备注。只追加不修改。
- `beacon_upstream_charges`：从上游日志同步的逐笔扣费。以（渠道、密钥指纹、上游日志 ID）唯一；不保存密钥，只存 SHA-256 前 16 位。保存上游额度、额度单位、分组倍率、匹配到的本站日志/客户/本站扣费。
- 成本 = 上游额度 ÷ 上游额度单位 × 当时生效进价，以百万分之一元整数存储，入库时定价一次，以后改价不重算。没有适用进价的记录为“待核算”，补录覆盖其时间的进价后才计价。
- 同步：主节点每 `BEACON_COST_SYNC_MINUTES` 分钟（默认 5，0 关闭）同步所有已配置进价的渠道；页面可立即同步。只支持 New API 类上游，其他上游显示同步错误。上游数值越界、负数时不入库。
- 匹配：按上游请求号匹配本站消费日志，最近 2 天内未匹配的记录每次同步重试。未匹配表示失败/重试请求、同一上游账户其他密钥或日志已清理，单独计数。
- 页面：人工账务 →“上游成本”，Root 浏览器会话专用。包含渠道进价与同步状态、最近观察到的上游分组倍率、按渠道/模型/日期/客户的成本汇总。“客户扣费（按售价）”只是扣除的额度，不是收入。

## 第二期：调价规则（已实现）

- 上游价格点 `beacon_upstream_prices`：同步时从上游日志 `other` 读取计费表达式（`expr_b64`）或旧倍率（`model_ratio`、`completion_ratio`、`cache_ratio`、`cache_creation_ratio`、`model_price`）与 `group_ratio`，按（渠道、模型、分组、倍率、表达式、额度单位）指纹去重；新组合即上游调价。只统计首次同步到的扣费。无缓存 token 的扣费按价格点复算并与实际扣额比对（误差 ≤ max(1, 0.5%)），记录一致与不一致笔数。
- 上游表达式只接受白名单写法：数字、token 变量、`len`、`tier("名称", …)`、`fixed`、`max/min/ceil/floor/abs` 与四则/比较/三元运算，长度 ≤ 2000，且须通过本站表达式冒烟测试；含 `param`、`header`、时间函数或其他内置函数的一律不用。每次同步最多检查 32 种不同表达式，避免挤占计费编译缓存。
- 成本与售价比较：按输入、输出、缓存读、缓存写（5 分钟/1 小时）、图片、音频分别用每百万 token 计算。成本 = 上游价格 × 上游分组倍率 × 渠道进价；售价 = 本站表达式 × 默认分组倍率 × 系统充值价格（`Price`，默认 ¥7.3/$1）。未单独定价的用量按结算规则归并：缓存读取并入输入；Claude 模型未定价的缓存写入免费，其他模型并入输入。表达式使用 `len` 时在 1K/150K/300K/1M 上下文各取一次。
- 规则 `beacon_pricing_rules`：默认规则（模型名为空）加按模型覆盖。字段：方式（按成本加价 / 固定售价只提醒）、目标加价率、最低加价率提醒、自动生效、跟随降价、单次最大调整幅度，均以基点存储。默认：按成本加价 30%，提醒 15%，确认后生效，不跟随降价，单次 50%。
- 计算：以已启用渠道中所需系数最大的一家（最贵）为成本基准，系数 = max(各用量 (1+目标) × 成本 ÷ 售价)；变化不足 1% 不提议。新表达式把每个“数字 × token 变量”和 `fixed()` 价格乘以系数并向上取 4 位有效数字，条件、档位名、请求规则倍数不变；结果须在各探测向量上等于原价 × 系数（误差 ≤ 0.11%），否则标记“写法无法自动调价”。有用量售价为 0 而上游收费时标记且不调价。
- 建议 `beacon_price_proposals`：记录旧/新表达式、定价版本、系数、依据渠道明细。价格版本变化后建议失效；被忽略或失败的同一建议不再重复提出；应用走 `UpdateModelPricing`（版本冲突检查、校验、缓存刷新），对所有客户（含已充值余额）下一次请求生效，已计费请求不变。
- 自动生效须同时满足：规则开启自动；系数在 ±单次最大幅度内；依据价格点至少复算一致 1 笔且无不一致；该模型 24 小时内没有自动调价。否则留作待确认。
- 触发：每次成本同步后、保存规则或进价后、页面“立即重新计算”。新建议、自动调价、自动失败及新低于最低加价率的模型通过渠道通知发送给接收渠道通知的管理员（默认 Root）。
- 页面：人工账务 →“调价规则”，含默认规则、待确认调价（成本/当前售价/调价后约值/表达式对比，应用需二次确认）、模型成本与售价表（明细与单独规则）、调价记录。
